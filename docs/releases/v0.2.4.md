# v0.2.4 — Parallel input processing, the instrumentation to tune it, and contract-independent output hardening

**Released:** 2026-06-27 · **Lifecycle:** alpha (interface-stability track; external contributions welcome)

v0.2.4 is a performance + tunability minor for high-volume `extract-multi`, building directly on v0.2.3's aggregate output with the performance follow-on it flagged. The headline is **parallel input processing**: `--input-workers N` runs each input's read+parse **plus** its full per-recipe application across N workers within one invocation, and a single ordered committer applies the results in input order — so the per-input long pole at high file counts scales toward available cores, with **byte-identical output at every worker count**. Paired with it, the opt-in **`--stats`** flag prints an end-of-run effective-CPU and throughput summary so you size `--input-workers` by measuring your own workload rather than guessing from core count. Around those, two contract-independent hardening items — `json`/`ndjson` naming clarity and additive manifest input-accounting integers — plus logging hardening round out the release. Everything is additive: defaults are byte-for-byte unchanged, the v0.2.0–0.2.3 surface (cloud I/O, reference-table lookup, multi-recipe single-pass extract, aggregate output) is unchanged, and the supported platform matrix is identical to 0.2.3.

## Features

### Parallel input processing — `--input-workers N` (`input-parallelism`)

Once the per-recipe re-parse is amortized by `extract-multi`, the remaining per-invocation cost at high file counts is **per-input processing** — read+parse **plus** each recipe's application to that input (signature/applicability matching, extraction, `min_occurrences` checks). By default that runs single-threaded: one invocation pins roughly one core regardless of input count. `recipes run extract-multi --input-workers N` runs that work across **N workers within the single invocation** — each worker parses an input and runs its full per-recipe application into a worker-local bundle — and a single ordered committer applies the bundles in input order:

- **Byte-identical output at every worker count.** The concurrency covers parse **and** application; only the durable commit — writing, the per-input spool barrier, ledgers, manifest accounting, shard rolling, and cloud publish — stays single-owner on the ordered committer. Records emit in resolved input order (`--file-list` / `--files` order, or sorted `--input-path` discovery order) regardless of which worker processed which input, with the same per-invocation provenance manifest and the same per-input/per-recipe failure attribution. That determinism is the load-bearing guarantee, validated under `-race` at high worker counts and confirmed by real-world dogfood runs (`--input-workers` 1 ≡ 4 ≡ 8, byte-identical).
- **Local and cloud.** `--input-workers > 1` works with local and cloud (`s3://`) aggregate and per-input output. Cloud shard publishes stay on the same single ordered committer (deterministic shard order, one object per shard) and cloud inputs are staged before any worker starts, so concurrency never changes the cloud publish, proactive byte-cap, partial-publish, or publish-fatal semantics.
- **Bounded memory, records never dropped.** A per-input bundle limit (record count and approximate bytes) plus a cross-input in-flight ceiling bound the worker look-ahead. An over-limit input fails deterministically during bundle construction, with guidance to split the input or reduce its per-input output — records are never silently dropped (streaming/spill for very large per-input outputs is planned). A panic in worker parse or application is contained as a per-input failure (recorded under `--continue-on-error`, fatal under fail-fast), never a process crash.
- **Safe defaults.** The default is `1` (serial, byte-identical to earlier releases); a value below `1` is rejected. Worker concurrency is recorded in the replayable `cli.argv_sanitized` only when it deviates from the default.

**Where it helps.** Both regimes scale: **parse-bound** runs (large or deeply-structured documents, especially with sparse extraction — a few records pulled from a big document) **and** the **tiny-file regime** (tens of thousands of small inputs, often across several recipes) both move toward the available cores instead of plateauing near one core, because the per-input application that dominated the previously serial drain now runs in the workers. The gain flattens once the single ordered committer — or an external ceiling (storage bytes/sec, IOPS, an object-store/API quota) — becomes the limit, so it helps most when per-input work is CPU-bound _and_ storage serves concurrent reads.

### Tune it by measuring — `--stats` (`run-stats`)

`recipes run extract-multi --stats` prints an opt-in end-of-run diagnostic block to **stderr** so you can size `--input-workers` from Sumpter's own output instead of guessing:

```text
extract-multi --stats (diagnostic; observed counters, not a recommendation)
  wall:          12.4s
  inputs:        50000 (4032.3/s)
  input bytes:   1430.2 MiB (115.3 MiB/s)
  input-workers: 4
  GOMAXPROCS:    8 (logical CPUs: 8)
  effective CPU: 3.10 cores (~78% of 4 input-workers)
```

- **Observed counters only — never a recommendation.** It reports wall clock, inputs and inputs/s, best-effort input bytes + MiB/s, the input-workers value, `GOMAXPROCS` + logical CPU count, and **effective CPU** (process user+sys CPU ÷ wall) shown as cores and as a percentage of input-workers.
- **Off the deterministic path.** Stats are nondeterministic, so they stay entirely off the artifact path: no record fields, no provenance manifest fields, no schema change, and `--stats` is not recorded in `cli.argv_sanitized`. Records and the manifest are byte-identical with `--stats` on or off.
- **Best-effort and degrading.** Input bytes come from already-resolved source sizes (no extra reads, no cloud calls) and show `unavailable` when sizes are not cheaply available; process CPU is read via `getrusage` / `GetProcessTimes` and shows `unavailable` on platforms where it cannot be read — a stats failure never fails the run.

### Tuning `--input-workers`

Input-parallelism and `--stats` are built to be used together. Rather than setting N to your core count, run `--input-workers 1`, then `N`, then `2N` with `--stats` and stop when throughput (inputs/s or MiB/s) plateaus. The right N depends on where your workload bottlenecks:

- **Low effective CPU + throughput still rising as N grows** — workers are waiting and more may help; raise N and re-measure. The right N can **exceed core count** for stall/latency-bound work.
- **Low effective CPU + throughput flat as N grows** — the ceiling is elsewhere (storage bytes/sec, IOPS or object-store/API quota, decompression/acquisition throttling, or the serial output drain), not CPU; more workers won't help.
- **High effective CPU near `GOMAXPROCS` + throughput flat** — you are CPU-bound and near the useful limit for this workload.

A low effective-CPU reading is **headroom to test, not proof** that adding workers will help. See the `--input-workers` section of [`docs/extract-workflow.md`](../extract-workflow.md) for the full tuning walkthrough.

### `json` / `ndjson` format-name clarity (`format-naming`)

The recipe output `format` token is now documented unambiguously: `json` is the legacy/canonical token and `ndjson` is a first-class accepted alias for the same writer family. Both emit newline-delimited JSON (NDJSON/JSONL) record envelopes and are **behavior-identical**, and neither produces a single-file JSON array or object. This is docs and recipe-schema descriptions only — zero breakage, no code-path change, and no deprecation warning. A future canonical flip (making `ndjson` the primary token) and a real single-file JSON-array format remain possible later decisions, not part of this release.

### Manifest input-accounting integers (`manifest-completeness`)

Aggregate provenance manifests gain four optional top-level integers — `inputs_total`, `inputs_applied`, `inputs_not_applicable`, `inputs_failed` — so a consumer can reconcile completeness from a single place rather than walking the full `inputs[]` inventory. They mirror the closed input-disposition enum exactly and satisfy the reconciliation invariant `inputs_applied + inputs_failed + inputs_not_applicable == inputs_total == len(inputs)`. They are emitted only on aggregate manifests with an authoritative gap-free inventory and are omitted on per-input/default manifests and on `incomplete:true` manifests, so existing manifests stay byte-identical. The required schema set is unchanged. This is contract-independent: a floor miss stays counted in `inputs_failed` (disposition `failed` with reason `min_occurrences_violation`), and the semantic `status` enum (`complete` / `partial` / `incomplete`) is deferred to the v0.3.0 data-artifact contract.

### Logging hardening

`logging.GetLogger()` now returns a shared no-op logger when none is configured, closing a latent nil-logger panic class in tests and future non-CLI entrypoints, so both `GetLogger().Method(...)` and an assigned-then-called logger are safe when the global logger is unset. A `forbidigo` lint rule now bans the `GetLogger().Method()` call pattern, enforcing the package-level `logging.Info` / `Warn` / `Error` house style as a gate.

## Compatibility & notes

- **All-additive.** `--input-workers` defaults to `1` (serial, byte-identical to 0.2.3) and `--stats` is opt-in and off the deterministic path, so records and the provenance manifest are byte-identical with either on or off. `json` / `ndjson` behavior is unchanged. The manifest required set is unchanged; the new input-accounting integers are optional and appear only on aggregate manifests.
- **`--input-workers` is a throughput knob**, not a blanket speedup. It parallelizes per-input read+parse and application; only the durable commit (writing, the per-input spool barrier, ledgers, manifest accounting, shard rolling, cloud publish) stays single-owner on the ordered committer, to preserve byte-identical output. Gains scale toward available cores when per-input work is CPU-bound and storage serves concurrent reads, and flatten once the committer or an external ceiling becomes the limit.
- **Provenance sidecar (`sumpter.provenance/v1`)** gains the four additive `inputs_*` integers on aggregate runs; existing manifests remain valid.
- **Platforms:** the supported prebuilt matrix is unchanged from 0.2.0–0.2.3 — linux amd64/arm64, darwin **arm64**, windows amd64/arm64. Intel-Mac users build from source.
- **Alpha:** interfaces may still change between minor releases; external pull requests are welcome.

## Deferred / follow-ups

- **`format-naming` canonical flip** — making `ndjson` the canonical token (with `json` as the compat alias) is a later option, not taken in this release.
- **`manifest-completeness` `status` enum** — the semantic `complete` / `partial` / `incomplete` vocabulary lands with the ratified v0.3.0 data-artifact contract.
- **Machine-readable run statistics** — a `run_stats` manifest block (vs the current stderr-only diagnostic) is a future contract decision, not this release.
- **`extract` polymorphic-correctness hardening and parquet-to-cloud publish** remain v0.2.5-conditional, and the **v0.3.0 data-artifact contract** (ratified artifact/parent-manifest and parquet schemas, optional runtime envelope validation) runs on its own track.
- **Cloud range-reads, cloud-side indexing, GCS/Azure providers, DuckDB/Arrow, service health endpoints, and repair modes** remain roadmap items, as in 0.2.3.
