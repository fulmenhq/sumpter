# v0.2.3 — Aggregate output, schema-backed records, and a clean-tree format gate

**Released:** 2026-06-25 · **Lifecycle:** alpha (interface-stability track; external contributions welcome)

v0.2.3 is a feature minor driven by real-world dogfooding of large many-small-input
extraction runs. The headline is **aggregate output**: a run over many inputs can now
stream **one** NDJSON file per recipe per invocation instead of one output file per input,
turning a per-input file-creation bottleneck into a single streamed write — with
deterministic record ordering, rolling shards, and per-shard provenance digests. Around it,
the **record envelope** is now schema-backed (a Draft 2020-12 JSON Schema for one emitted
NDJSON row, with build-time meta-validation), `extract-multi` gains the full
`--file-list` / `--files` / `--input-path` input-selection set with deterministic aggregate
ordering, and a one-time **whole-tree format normalization plus a full-tree format gate**
keeps documentation and config drift from silently re-accumulating. The v0.2.0–0.2.2
surface (cloud I/O, reference-table lookup, multi-recipe single-pass extract) is unchanged,
and the supported platform matrix is identical to 0.2.2.

## Features

### Aggregate output mode (`--output-mode aggregate`)

By default each input produces its own output file. Over a set of many small inputs (dozens
to thousands), creating one output file per input makes **file fan-out**, not parsing, the
bottleneck. `--output-mode aggregate` streams all of a recipe's records into a **single**
NDJSON file per invocation:

- **Deterministic ordering.** Records are emitted in **input order × intra-input
  `record_num`**. For `--file-list` / `--files`, the supplied order is authoritative; for
  `--input-path` discovery, inputs are sorted before ordinals are assigned. The payload is
  byte-stable for the same input subset (only runtime-stamp fields vary).
- **Rolling shards.** `--aggregate-max-records <n>` and `--aggregate-max-bytes <bytes>` roll
  the stream into sequential shards proactively on the running record/byte count, so a long
  run stays bounded without buffering everything.
- **Input-set provenance.** Because an aggregate file no longer maps to one input by name,
  the provenance manifest carries a gap-free `inputs[]` inventory (each input's `sha256`,
  `record_count`, and disposition, with ordinal = position in `inputs[]`) plus, per shard,
  an `aggregate_outputs[]` entry with that shard's own `sha256`, `record_count`, and
  contributing input-ordinal span. The **manifest, not filename parsing, is authoritative**
  for what an aggregate run produced. An input whose records straddle a shard cap appears in
  **both** adjacent shards' ordinal spans (the spans locate coverage, they do not partition).
- **Partial-failure handling via a per-input barrier.** `--continue-on-error` and recipe
  `min_occurrences` floors are supported for **both local and cloud** aggregate output: each
  input's records are buffered and committed to the shard only when that input succeeds, so a
  failed or floor-missing input never contributes partial records to the stream and is
  recorded in `failures.json` and the `inputs[]` inventory. Without `--continue-on-error`,
  aggregate is fail-fast and an input failure aborts the run.
- **Cloud.** Aggregate output writes to `s3://` through the existing stage-and-publish
  boundary (single atomic PUT per shard, withhold-aware, credential-handle indirection). A
  cloud aggregate run **requires `--aggregate-max-bytes`** at or below the single-PUT limit
  (5 GiB) and is rejected at plan time otherwise. If publishing fails part-way, the manifest
  is marked `incomplete:true` and enumerates exactly the shards that committed, so orphaned
  output is always manifest-discoverable.
- **With `extract-multi`.** `--output-mode aggregate` applies to multi-recipe runs too: each
  recipe gets its **own** aggregate writer and shard sequence under its
  `<output-path>/<recipe-id>/` subdirectory, with no cross-recipe record bleed.

See [`docs/extract-workflow.md`](../extract-workflow.md) "Aggregate output mode" for worked
local and cloud examples.

### Batch input selection & deterministic ordering (`--file-list` / `--files` / `--input-path`)

`extract-multi` now accepts the full input-selection set already available to single-recipe
`extract` — `--file-list <path>`, `--files a.xml,b.xml`, and `--input-path <dir>` — as
**mutually exclusive** options:

- **`--file-list`** is the batch input for large or precisely-scoped sets: a newline-delimited
  list of input references (local paths or `s3://` URIs), with no directory walk and no shell
  argv ceiling, so an upstream selection step can hand Sumpter exactly the file set —
  including an arbitrary subset no single path glob can express. Relative entries resolve
  against the list file's directory; listed order is preserved.
- For **aggregate** runs this order is load-bearing: **aggregate ordinals are assigned in
  `--file-list` (or `--files`) order**, so the output ordering is fully operator-controlled
  and reproducible. `--input-path` sorts discovered inputs before assigning ordinals.

### Schema-backed record envelope (`record-envelope`)

The emitted extract record row (one NDJSON line) is now backed by a **Draft 2020-12 JSON
Schema** — previously the durable envelope was governed only by docs and tests, while the
provenance/disposition/failure sidecars were already schema-backed.

- A new `schemas/extract/v0.1.0/extract-record-envelope.schema.json` validates one emitted
  row: a closed top-level envelope (`_runtime` + `extract`, with `extract.data` required) and
  an open, additively-extensible `_runtime`/payload.
- Each row now self-identifies via `_runtime.envelope_schema = "extract-record-envelope/v0"`
  (additive; major-only so additive schema revisions do not churn the per-row value), so a
  future contract mapping stays additive and consumers can validate the stream against a
  stable contract.
- A build-time meta-validation target (`make extract-output-contract-check`, wired into
  `make check-all`) validates fixture rows against the schema, and a round-trip test validates
  a live-emitted record — keeping the schema honest as the envelope evolves.

This is **contract-independent** output hardening: it schematizes what Sumpter already emits,
with no behavior or recipe-semantic change.

### Whole-tree format normalization & gate (`format-normalize`)

A one-time repository-wide format sweep (Markdown / JSON / YAML via `goneat format`, plus an
end-of-file-newline pass) normalizes accumulated whitespace drift, and a **full-tree format
gate** plus a VERSION-drift guard now run in CI. Previously the format check compared only
changed-vs-`main`, so unrelated drift could ride into an unrelated PR; the full-tree gate
means every branch forks from a clean tree and drift can never silently re-accumulate.

## Compatibility & notes

- **All-additive.** `--output-mode aggregate` and the aggregate cap flags are opt-in; the
  default remains one output file per input, byte-for-byte as in 0.2.2. The record-envelope
  schema describes existing output (the new `_runtime.envelope_schema` field is additive;
  existing consumers that ignore unknown `_runtime` fields are unaffected). The format sweep
  touches only whitespace/EOF, not content.
- **Aggregate is NDJSON-only.** Aggregate output streams NDJSON; JSON-array and Parquet
  outputs continue to write per-input files. Cloud aggregate requires `--aggregate-max-bytes`
  ≤ 5 GiB.
- **Provenance sidecar (`sumpter.provenance/v1`)** gains an additive `aggregate_outputs[]`
  block on aggregate runs and a gap-free `inputs[]` inventory; existing manifests remain
  valid.
- **Platforms:** the supported prebuilt matrix is unchanged from 0.2.0–0.2.2 — linux
  amd64/arm64, darwin **arm64**, windows amd64/arm64. Intel-Mac users build from source.
- **Alpha:** interfaces may still change between minor releases; external pull requests are
  welcome.

## Deferred / follow-ups

- **Aggregate-output performance follow-on** — a throughput optimization identified during
  dogfooding is sequenced for v0.2.4 (not a v0.2.3 blocker).
- **`json` / `ndjson` format naming** clarification and the **manifest-completeness signal**
  (input-accounting fields) are sequenced as separate follow-ups.
- **Optional runtime envelope validation** (a `--validate-output` mode and the full
  validation ladder) is deferred to the v0.3.0 data-artifact-contract work, alongside the
  contract-coupled artifact/parent-manifest and parquet schemas.
- **Cloud range-reads, cloud-side indexing, GCS/Azure providers, DuckDB/Arrow, service
  health endpoints, and repair modes** remain roadmap items, as in 0.2.2.
