# v0.2.2 — Multi-recipe single-pass extraction

**Released:** 2026-06-23 · **Lifecycle:** alpha (interface-stability track; external contributions welcome)

v0.2.2 is a feature minor driven by real-world dogfooding of large
multi-projection extraction runs. The headline is **`extract-multi`**: when
several recipes extract different projections from the **same** input set,
Sumpter now reads and parses each input file **once** and dispatches the parsed
document to every recipe, instead of re-reading and re-parsing every file once
per recipe. Two ergonomics features make that workflow adoptable for production
pipelines — a shared run-level `--parameter` passthrough and derive-only
`source_extraction` captures. The v0.2.0/0.2.1 surface (cloud I/O, reference-table
lookup, list-typed parameters, batch file-list input) is unchanged, and the
supported platform matrix is identical to 0.2.1.

## Features

### Multi-recipe single-pass extract (`extract-multi`)

When a set of recipes each extract a **different projection** from the same
inputs — say a per-record summary, a line-item detail view, and a rollup —
running them as separate `recipes run extract` invocations re-reads and re-parses
every input file once per recipe. At high file counts (many small files) that
redundant parse is the dominant cost.

`recipes run extract-multi <workspace>...` applies all of them in a single pass:

- Each input file is read and **parsed once**, then the parsed document is
  dispatched to every signature-matched recipe. The per-recipe re-parse is
  amortized from ~N× to 1× across N recipes — the parse-once value-prop.
- Each recipe writes to its **own** isolated subdirectory under `--output-path`,
  named by the recipe `id` (`<output-path>/<recipe-id>/`): its records,
  provenance manifest, and — when applicable — `dispositions.json` /
  `failures.json`. One recipe can never read or clobber another's output.
- **Per-recipe** state — output, formats, `defaults.parameters`, reference tables,
  and credential handles — comes from each recipe's own manifest. **Shared**
  across recipes — the input set, the output root, and run-level controls
  (`--continue-on-error`, credentials, the run id). The run id resolves once
  (flag → `SUMPTER_RUN_ID` → generated) so every recipe's provenance ties to one
  invocation.
- **Failure handling follows the input-vs-recipe boundary.** A read/parse/acquire
  failure is **input-level** (it affects every recipe's view of that file); an
  applicability, signature, extraction, `min_occurrences`, or output failure is
  **recipe-level** — isolated to that recipe's own `failures.json` (under
  `--continue-on-error`) without aborting the others.

**Scope (v0).** `extract-multi` writes **JSON/NDJSON** output only; a recipe
declaring another format (e.g. Parquet) is rejected — run it with single-recipe
`recipes run extract` instead. The large-file **streaming** path is not supported:
each file is parsed once into memory, so a file large enough to route to streaming
is rejected (`--allow-large-files` does not relax this). Cross-recipe joins,
ordering, and combined-record assembly are out of scope — the pass amortizes the
read + parse, nothing more.

See [`docs/extract-workflow.md`](../extract-workflow.md) "Run multiple recipes in
one pass" for a worked example showing the per-recipe output tree.

### Shared run-level `--parameter` (`multi-parameter`)

Single-recipe `recipes run extract` accepts a repeatable `--parameter key=value`
that overrides a recipe's `defaults.parameters` and is injected into every record.
`extract-multi` adds the same control at the **run** level: a `--parameter`
supplied to `extract-multi` is layered over **every** recipe's
`defaults.parameters` in the pass, with the **same** override, collision, and
typed-value (scalar or JSON-list) semantics as the single-recipe flag.

- Per-recipe manifest parameters stay authoritative for per-recipe config; the
  shared passthrough carries only the genuinely **per-run** keys every recipe
  shares — for example a per-run provenance/version stamp or an operator runtime
  value that has no manifest or input-path home.
- It satisfies each recipe's `parameters_required` independently, and the CLI
  value wins uniformly over each recipe's manifest default for the same key.
- A shared key that collides with any recipe's `field_mappings[].output_field`
  fails the whole run at **plan-load preflight**, before any output is written.
- `--parameter` is **not** a credential transport. Secret-shaped parameter values
  (`token`, `secret`, `password`, `credential`, …) are redacted by parameter key
  in the recorded provenance argv — an improvement that also applies to
  single-recipe runs.

### Derive-only `source_extraction` captures (`internal-fields`)

`source_extraction` patterns derive file-level fields from the source `filename`,
`relative_path`, or `absolute_path`, and every captured field is normally emitted
onto the record. When a capture is wanted **only** as an expression intermediate —
to derive another field, never as a column of its own — mark the pattern
`internal: true`:

```yaml
defaults:
  source_extraction:
    - id: grain-tag
      source: filename
      pattern: '^(?P<source_grain>unit|batch)-.*\.xml$'
      internal: true # drives expressions; not written to the record
```

- The captures are available in `field_mappings[].expression` scope (so a derived
  `output_field` resolves) but are **stripped from the record body across every
  sink** (JSON, NDJSON, Parquet) — no stray intermediate column.
- The flag defaults to `false`, so existing patterns keep emitting their captures
  unchanged.
- Internal captures still participate fully in `source_extraction_required` (a
  required internal capture still fails per file when absent) and in the
  capture↔`output_field` / capture↔`defaults.parameters` collision checks.
- A capture name declared on **both** an `internal: true` and a non-internal
  pattern is rejected at plan validation, so a capture's emit visibility is
  unambiguous.

> **`internal: true` is an output-shaping control, not a redaction or secrecy
> mechanism.** The captured value still lives in expression scope, so a recipe
> author can deliberately re-emit it (or a value derived from it). Do not rely on
> it to keep a sensitive value out of output; for that, do not capture the value.

## Compatibility & notes

- **All-additive.** `extract-multi` is a new subcommand; the shared `--parameter`
  and `internal: true` are opt-in. Single-recipe `recipes run extract` behavior,
  output formats, and the provenance sidecar schema (`sumpter.provenance/v1`) are
  unchanged. A recipe with no `internal: true` pattern, run outside `extract-multi`,
  behaves byte-for-byte as in 0.2.1.
- **Platforms:** the supported prebuilt matrix is unchanged from 0.2.0/0.2.1 —
  linux amd64/arm64, darwin **arm64**, windows amd64/arm64. Intel-Mac users build
  from source.
- **Recipe schema:** `source_extraction[].internal` (boolean, default `false`) is
  the only additive schema change; existing recipes remain valid.
- **Alpha:** interfaces may still change between minor releases; external pull
  requests are welcome.

## Deferred / follow-ups

- **Input-handle provenance in multi runs** — record the effective shared input
  credential handle in each recipe's provenance for full auditability. Fast-follow.
- **`relative_path` log-message tidy** — a discovery message still says "`--files`
  mode" even when `--file-list` was used. Cosmetic.
- **`extract-multi` format and size scope** — Parquet (and other non-JSON/NDJSON
  formats) and the streaming/large-file path are out of scope in v0; both remain
  on the roadmap.
- **Cloud range-reads, cloud-side indexing, GCS/Azure providers, DuckDB/Arrow,
  service health endpoints, and repair modes** remain roadmap items, as in 0.2.1.
