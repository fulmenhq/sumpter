# v0.4.0 — Draft Release Notes

**Undated draft; not a release announcement.**

Recipe-driven extraction from XML, JSON, and NDJSON, with route-specific
streaming and indexed processing.

| Input route     | Supported source formats           |
| --------------- | ---------------------------------- |
| Extract files   | `xml`, `json`, `ndjson`            |
| Inspect         | `xml`, `json`                      |
| Record analysis | `xml`                              |
| Record indexes  | `xml`, `json`; uncompressed source |
| Extract-multi   | `xml`                              |

JSON streaming and indexed extraction, and NDJSON extraction, need a
record-scoped recipe and an eligible selector and output. NDJSON is not an
inspect or index input; JSON/NDJSON record analysis is refused. The indexed
source document must be uncompressed; JSON or optional seekable-zstd index
storage is independent. See the [input-route matrix](../extract-workflow.md#input-route-support).

## Inputs and recipes

- Declare `defaults.input.format` and the matching signature `format_type`;
  formats are not inferred from names/content. XML remains the default, and
  reserved `protobuf` signatures fail at load.
- XML and JSON use one DSL and XPath grammar, not one unchanged recipe.
  JSON members become elements, arrays repeated siblings; JSON has no attribute
  or namespace axes. Null/empty arrays bind absent, unlike XML's empty string.
  Parsing preserves numeric lexemes; XPath numeric operations use floating
  point. String mappings and `value_text` preserve identifiers above 2^53.
- JSON/NDJSON require UTF-8 and accept one leading UTF-8 BOM. Raw source
  digests and absolute record offsets include its bytes; record ranges do not.
  Invalid UTF-8, duplicate keys, excessive nesting, trailing values and
  truncation fail loudly. Provenance `inputs[].format` records the parsed syntax.
- JSON below the large-file threshold uses DOM. Above it, eligible
  record-scoped recipes stream; blockers produce `route_unsupported` rather
  than a silent fallback. `--allow-large-files` opts into whole-document JSON
  parsing. NDJSON always reads one object per nonblank line, with no document
  route or applicability predicate. Empty/blank-only NDJSON fails.
- Path discovery defaults to `*.xml`, `*.json` or `*.ndjson` for the declared
  input; `.jsonl` trees need an explicit include pattern. Zero discovered inputs
  now fail before output creation; valid parsed input with zero selected
  matches can still succeed under the default zero floor.
- CLI path overrides for `recipes run extract` resolve against the working
  directory. Manifest paths remain recipe-relative; file-list entries remain
  list-file-relative. Dry runs check named local/cloud inputs without fetching
  object bytes or writing outputs. Unavailable inputs have `input_unavailable`
  dispositions, and continue-on-error runs remain non-zero/partial.

## Inspection and indexes

- `inspect --input-format json` profiles key paths, counts, value kinds and
  samples. JSON config generation writes a loadable starter with commented
  signature/manifest declarations. Record analysis stays XML only.
- Reports use `inspect-report/v0.1.2`: `input.format`, authoritative path
  `segments`, and JSON `value_kinds`. Display paths escape dots/backslashes;
  Markdown names/samples render as inert text.
- JSON indexed/parallel extraction requires a record-scoped signature and
  selector equality, with raw-range hashes checked before parsing. The
  indexed JSON record cap defaults to 100 MiB when zero; XML zero remains
  unlimited. Structural/range checks are not selector completeness:
  `index verify --input-format json` rescans selection; extraction's
  `--verify-index` binds whole-source integrity and identity instead.
- New indexes use `record-index/v0.1.3` with required `source.format`;
  seekable headers use `record-index-szst/v0.1.2`, nested `records.layout`,
  and a contained sibling records file. Current readers retain older XML-only
  index support. Earlier readers refuse new indexes for verify/extract and
  new seekable headers for stream, but earlier JSON-store `index stream` may
  print metadata and exit 0. That exit is not compatibility/refusal proof.
- Schemas use host-independent `contract://` ids, per-version manifests and
  a digest catalog. Consumers matching old hosted ids need updating.

## Output and diagnostic boundaries

Input parsing is separate from output streaming. JSON DOM loads a document;
record routes retain parser, active-record, writer and reordering state. A
wide object or file-spanning JSON record can need input-scale memory. Parquet,
mixed outputs, sequential floors and ambiguous indexed floors stay buffered;
historical XML benchmarks are not JSON memory evidence.

The file-output tokens `json` and `ndjson` share one JSONL writer. Stdout and
library deliveries are provisional until terminal success and cannot be retracted;
consumers must handle failure before committing effects. File-backed record
sinks withhold staged rows on pre-commit input/extraction failure, not every
terminal error: later validation/publish failures can leave committed local
files, and earlier completed inputs can remain. `pipefail` detects errors,
not rollback. See the [record-sink contract](../extract-workflow.md#recordsink-streaming-contract).

Human `envinfo` adds a built-in route section; both human XML renderers qualify
`<50MB RSS` as an XML input-tokenization design target, not a measured run or
JSON bound. Machine payload/schema values, export and single-purpose route
surfaces remain unchanged.
