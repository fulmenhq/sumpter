# Sumpter v0.1.5 Release Notes

**Release Date:** 2026-05-26
**Theme:** Release readiness, recipe applicability gates, and resilient multi-file extraction
**Status:** Prepared for release

## Overview

v0.1.5 is a focused hardening release after v0.1.4. It keeps the public surface narrow while proving the release pipeline introduced in v0.1.4, improving CI coverage around release artifacts, and making mixed-input extraction cohorts easier to operate.

The release has three threads:

1. **Recipe applicability.** Recipes can declare a file-level XPath predicate that runs before signature matching. Inputs that do not apply are reported as such instead of being treated as extraction failures.
2. **Failure isolation.** Multi-file extraction can continue past recoverable per-input failures and emit a schema-backed failure manifest alongside successful sibling outputs.
3. **Release confidence.** CI now exercises the release-build path before merge, releases publish as drafts until signing is complete, and the Go/linter toolchain is aligned on Go 1.26.

## What's new

### Recipe applicability gates

Recipes may reference an optional `assets.applicability` file. That file contains a top-level `applicability:` object with a binary predicate:

```yaml
applicability:
  type: xpath
  expression: "boolean(/*[local-name()='Document'])"
  description: "Only run this recipe for document-style XML inputs"
```

Applicability runs before signature matching:

- A false predicate produces a `not_applicable` disposition, extracts no records, and does not count as a failure.
- A true predicate proceeds to normal signature matching and extraction.
- Predicate evaluation errors fail loud.
- Unsupported mode combinations fail loud instead of silently skipping applicability.

Applicability assets participate in the recipe content hash and provenance material, so behavior-bearing recipe assets remain part of the reproducibility surface.

### Disposition summaries

Applicability-aware runs add per-input disposition fields to provenance entries and write a lightweight `dispositions.json` summary at the output root. The summary uses `schema_version: extract-dispositions/v0.1.0` and is validated by `schemas/extract/v0.1.0/dispositions.schema.json`.

The closed disposition reason set includes:

- `applicability_predicate_false`
- `signature_mismatch`
- `min_occurrences_violation`
- `parse_error`
- `validation_error`
- `internal_error`

### Continue-on-error failure manifests

`--continue-on-error` is available on both:

```bash
sumpter extract files --continue-on-error --output-path outputs ...
sumpter recipes run extract --continue-on-error --output-path outputs ...
```

In v0, the flag requires `--output-path` because Sumpter needs a durable root for successful sibling outputs and the failure manifest. Recoverable per-input failures are written to `<output-path>/failures.json`; successful inputs still emit their normal outputs. The command exits non-zero if any input failed so schedulers can distinguish a partially successful cohort from a clean cohort.

The failure manifest uses `schema_version: extract-failures/v0.1.0` and is validated by `schemas/extract/v0.1.0/failures.schema.json`. The closed failure reason set is:

- `parse_error`
- `signature_mismatch`
- `min_occurrences_violation`
- `validation_error`
- `internal_error`

Durable output failures and failure-manifest write failures remain terminal. `--continue-on-error` isolates recoverable per-input failures; it does not hide write-path failures.

### Signature mismatch diagnostics

Inputs that miss a recipe signature and later encounter declared `min_occurrences` floors now surface `signature_mismatch` with confidence and threshold details. Genuine post-signature `min_occurrences` shortfalls keep the existing `min_occurrences_violation` reason.

### CI and release hardening

v0.1.5 hardens the release path rather than adding broad release automation:

- `.github/workflows/ci.yml` runs PR-time quality gates and a `make release-build` dry run in the release container shape.
- `.github/workflows/release.yml` builds with Go `1.26.3` and publishes GitHub Releases as drafts first.
- `make release-guard-tag-version` fails loud unless the requested release tag matches `VERSION`.
- `SUMPTER_RELEASE_TAG` is the preferred release tag environment variable; `RELEASE_TAG` remains available for one-off invocations.
- PGP verification now checks for expected PGP output when PGP signatures were produced.
- CI installs `golangci-lint` `v2.11.2`, matching the known-good Go 1.26-compatible linter.

## Behavior changes

- **Applicability runs before signature matching.** False predicates are not signature failures and do not count as extraction failures.
- **Applicability declarations are schema-shaped.** Predicate fields belong under the top-level `applicability:` key, not at the asset file top level.
- **`--continue-on-error` is opt-in.** Default behavior remains fail-fast.
- **`--continue-on-error` requires `--output-path` in v0.** Runs without a durable output root fail fast.
- **Partial cohorts exit non-zero.** A run with at least one recoverable input failure writes `failures.json` and exits non-zero.
- **Durability failures stay terminal.** Output-write and manifest-write failures are not converted into recoverable per-input failures.

## Deferred

- **Cloud URI I/O** remains deferred to a future cycle. v0.1.5 deliberately focuses on release hardening and local/multi-file extraction resilience.
- **Shell shfmt baseline cleanup** remains a dedicated housekeeping follow-up. The findings are visible in goneat hook output and non-blocking under current policy.

## Upgrade notes

- **Version bump.** `VERSION` is `0.1.5`. Binaries from this tag emit `v0.1.5` via `sumpter version`.
- **Go installation.** After the tag is published, install with:

  ```bash
  go install github.com/fulmenhq/sumpter/cmd/sumpter@v0.1.5
  ```

- **Recipe applicability files.** Place applicability predicates in their own YAML asset and reference them from the recipe manifest:

  ```yaml
  assets:
    signature: signature/signature.yaml
    extract: extract/extract.yaml
    applicability: applicability/applicability.yaml
  ```

- **Failure handling.** Consumers that opt into `--continue-on-error` should read both normal output manifests and `failures.json`. Do not treat a non-zero exit as equivalent to no useful output; inspect the manifest for per-input outcomes.
- **Release ceremony.** Use `SUMPTER_RELEASE_TAG=v0.1.5` for release targets. The release remains draft until the signing ceremony uploads checksums, signatures, public keys, and notes and then runs `make release-publish`.
