# v0.2.1 — Empty-element binding and batch file-list input

**Released:** 2026-06-20 · **Lifecycle:** alpha (interface-stability track; external contributions welcome)

v0.2.1 is a focused patch driven by dogfood feedback on a large (1.2M-row)
extraction run. It carries two independent fixes: a present-but-empty XML string
element now binds a defined `""` instead of an undefined value (so a common DSL
guard pattern no longer crashes), and a new **batch file-list input** lets an
orchestrator hand the engine an exact file set with no directory walk. The new
surface from v0.2.0 (cloud I/O, reference-table lookup, list-typed parameters) is
unchanged; the supported platform matrix is identical to 0.2.0.

## Fixes

### Present-but-empty string elements bind `""` (`empty-element-bind`)

When an XPath *string* field maps to an element that is **present but empty**
(`<Name></Name>` or `<Name/>`), the field previously bound an **undefined** value
in DSL scope — while `boolean()` on the same node returned **true**. The two
disagreed, so the natural presence-guard pattern

```text
has_name ? upper(name) : "—"
```

crashed at evaluation with `undefined variable` precisely when the element was
present-but-empty. As of v0.2.1 the field binds the **empty string** — a defined
value that agrees with `boolean()` presence — and the guard evaluates normally.

This was a pre-existing defect surfaced by the 1.2M-row dogfood (rare but real).
The v0.2.0 documentation note describing the workaround already shipped; this is
the real fix. (#100)

### Behavior change — please review before upgrading

A recipe that previously **errored** with `undefined variable` on a
present-but-empty element now **succeeds**, producing `""` for that field. If a
recipe relied on that error to reject empty elements, add an explicit guard
(`string_length(field) > 0 ? … : …`). The **absent**-element case is unchanged —
absent and present-but-empty remain distinguishable (`boolean()` is `false` for
absent, `true` for present-but-empty); only the present-but-empty *string binding*
changed from undefined to `""`. The `dsl-reference` documentation already
documents the empty-vs-absent distinction.

## Features

### Batch file-list input (`input-prune`)

Large, mixed-grain corpora are often pre-selected upstream: the operator already
knows the exact set of files to extract, and that set is a scoped membership set
(e.g. a chosen `{day × partition}` cross-product), not a single path shape. Asking
the engine to walk a directory tree and rediscover that set is both slow and
imprecise.

v0.2.1 adds a batch **file-list** input that takes the set directly:

- **`extract --file-list <path>`** (CLI) and recipe
  **`defaults.input.files_from`** (manifest) read a newline-delimited list of
  input references — one per line.
- Entries are local paths or `s3://` / `file://` URIs; a scheme-bearing URI flows
  through the **same read boundary as `--files`**. A relative local entry resolves
  against the **list file's directory** (not the process CWD), so a list travels
  with its entries.
- Blank lines and `#` comments are ignored; listed **order is preserved**; an
  unsupported scheme or an effectively empty list **fails loud with line context**.
- The file-list path does **no directory enumeration** and is not subject to the
  `--files` argv ceiling — the decisive advantage at 10⁵–10⁶ files, where a
  comma-separated `--files` argument overflows the shell argument limit.
- `--file-list` is mutually exclusive with `--files` and `--input-path`; on a
  recipe run the CLI flag overrides the manifest. The recipe schema gains
  `input.files_from`.

Cloud (`s3://`) entries in a file-list are supported and verified end to end
against an S3-compatible endpoint (moto): the engine reads and classifies the list
so a cloud entry creates a credentialed session, then acquires it through the cloud
read boundary. (#101)

### `--input-path` discovery visibility (`input-prune`)

For the existing `--input-path <dir>` mode, directory enumeration is now legible:
it announces the root it is walking, reports the matched file count and elapsed
time on completion, and **warns loudly** once a walk crosses a slow threshold. An
accidental over-scope or a slow tree is now visible in the first seconds instead of
appearing as a silent multi-minute stall. Discovery results are unchanged — this is
visibility only. (#101)

## Compatibility & notes

- **Patch release:** no breaking interface changes beyond the documented
  present-but-empty binding behavior change above.
- **Platforms:** the supported prebuilt matrix is unchanged from 0.2.0 — linux
  amd64/arm64, darwin **arm64**, windows amd64/arm64. Intel-Mac users build from
  source.
- **v0.2.0 surface unchanged:** cloud I/O, reference-table lookup, and list-typed
  recipe parameters behave as in 0.2.0; the provenance sidecar schema
  (`sumpter.provenance/v1`) is unchanged.
- **Alpha:** interfaces may still change between minor releases; external pull
  requests are welcome.

## Deferred / follow-ups

- **File-list single-read refactor** — `extract` reads the list twice today (once
  to decide cloud-session need, once to discover refs); a later refactor will
  discover once and derive session-need from that slice.
- **`files_from` vs `mode` precedence** — `files_from` currently wins over a
  manifest `path` default; a follow-up will document the precedence or tighten
  manifest validation.
- **Directory-prune + streaming discovery** — include-derived directory pruning and
  streaming discovery callbacks are a separate upstream enhancement; a secondary
  `--input-glob` shortcut for naturally path-shaped subsets is deferred behind the
  file-list primary.
- **Cloud range-reads, cloud-side indexing, GCS/Azure providers, DuckDB/Arrow,
  service health endpoints, and repair modes** remain roadmap items, as in 0.2.0.
