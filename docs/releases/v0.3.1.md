# v0.3.1 — Opt-in process-run flight recorder

**Released:** 2026-07-14 · **Lifecycle:** alpha (interface-stability track; external contributions welcome)

v0.3.1 gives operators of long-running `recipes run extract-multi` batches a
portable local **flight recorder** under host-less `process-run/v0`: discover an
in-flight or retained run from an owner-only process card, follow settled
progress on an append-only NDJSON event stream, and — when data-artifact
descriptors are also enabled — read which published artifacts the sole terminal
event references. Nothing here replaces durable extract output; it is how you
watch the *process* without parsing workdir trees or coupling observers to
output paths.

Under the hood the release pins the contract, publishes the card and stream,
and bridges the terminal to successfully published `data-artifact/v0`
descriptors when both surfaces are enabled.

The release is **additive and opt-in**. Runs that never enable process-run
telemetry keep extract outputs, exit codes, and provenance manifests
byte-compatible with v0.3.0. Process-run flags and paths are omitted from the
sanitized provenance argv — they are operator telemetry surfaces, not portable
replay inputs.

This ships the **observe-only** half of process-run/v0 (watch a run). It does
**not** include a control socket or run-steering surface. The card is
telemetry-only in this release.

Operator notes live in
[`docs/process-run.md`](../process-run.md). The data-artifact producer profile
from v0.3.0 is unchanged; see
[`docs/data-artifact-producer-profile.md`](../data-artifact-producer-profile.md).

## Features

### Host-less process-run contract baseline

Extract resolves `process-run/v0` with the same host-less contract discipline
used for `data-artifact/v0` (shared resolution primitive; no second resolver).
Production pin checks use the process-run entry-bundle and sibling event-schema
digests against Crucible **`v0.1.19`** (entry-bundle
`sha256:4589befc1d0d3485744c7eea3dfb569ff79457f99996f2ee8313595489a7091b`,
event-schema
`sha256:7138fba72fea862d7964d6c235b1b93da0047e9eb76862be4d111701f887b12d`).
Neutral card and NDJSON event fixtures plus `make process-run-contract-check`
(wired into `make check-all`) keep the pin honest in CI and offline.

### Opt-in event stream

`extract-multi` can emit a single-writer process-run/v0 NDJSON stream
(`--process-run-events <path>`, or via the process-run enable path that places
`events.ndjson` under the runtime slot):

| Event | Role |
| --- | --- |
| `started` | Run open |
| `progress` | Settled input counters (`data.done` / `data.total`) |
| heartbeat | Liveness while work continues |
| exactly one terminal | `completed` \| `failed` \| `canceled` |

Setup and write failures are **fail-open** for telemetry (warn and continue
extraction). Stream files are exclusive-create, owner-only (`0600`). Placement
under the invocation’s effective home or workdir roots is rejected. CLI cancel
uses SIGINT/SIGTERM via context cancellation (no control channel).

The **terminal event is authoritative** for run outcome. Progress
`done == total` alone is not success — always read the final terminal. Process
completion is also independent of artifact completeness.

### Process card and reclaim

With process-run enabled (not stream-only), Sumpter publishes an owner-only
discovery root under a runtime directory:

```text
<runtime>/proc/<run_id>/reclaim.lock  # kernel advisory lock for stale takeover
<runtime>/proc/<run_id>/claim.json    # exclusive ownership lease + identity
<runtime>/proc/<run_id>/claim.taking  # optional mid-takeover diagnostic
<runtime>/proc/<run_id>/card.json     # discovery root while published
<runtime>/proc/<run_id>/events.ndjson # durable event stream
```

Runtime directory resolution: `--process-run-runtime-dir`, then
`SUMPTER_PROCESS_RUN_RUNTIME_DIR`, then `$XDG_RUNTIME_DIR/sumpter`, then a
temp-dir fallback. The runtime root must not sit under `SUMPTER_HOME` or the
workdir.

- Card payloads are pin-validated **before** publish; the final `card.json`
  appears only after a complete temp write (atomic no-replace hard-link; no
  rename fallback).
- **Clean exit** (including a normal failed extract): card withdrawn; claim
  becomes an `exited` tombstone; event stream **retained**.
- **Crash / kill**: live claim and card remain for discovery; stale reclaim
  requires a proven-stale `(pid, started_at)` via claim-token quarantine.
- **`reclaim.lock`** (flock / LockFileEx) is the sole mutual-exclusion authority
  for recovery and stale takeover; process death auto-releases; the lock inode
  is never unlinked by residue cleanup. `claim.taking` is diagnostic only.
- A live reused `run_id` is **fail-closed**. Ordinary placement/setup failures
  disable process-run and warn on stderr; extraction continues.

### Terminal → data-artifact bridge

When process-run telemetry **and** `--artifact-descriptor` are both enabled,
successfully published descriptors are attached to the sole terminal event as
`data.artifacts[]`:

| Field | Value |
| --- | --- |
| `artifact_id` | Exact published descriptor id (`urn:uuid:…`) |
| `lifecycle` | Exact descriptor lifecycle (never re-derived from the process terminal) |
| `descriptor` | Portable non-locator ref: `<artifact_id>#descriptor` |

Rules:

- Without `--artifact-descriptor`, `data.artifacts` is **omitted** (not `[]`).
- Refs register only after output **Publish** succeeds; publish failure remains
  an extract failure (not fail-open telemetry).
- Multi-recipe runs list only successful publications, in plan order.
- Process terminal class never rewrites artifact lifecycle — a failed process
  may still list a `complete` artifact.
- The bridge is **reference-only**: no output paths, cloud URIs, recipe IDs, or
  secret-bearing locators in the event stream.

## Compatibility & notes

- **All-additive / byte-compatible default path.** No process-run flags →
  pre-0.3.1 extract behavior and provenance.
- **Telemetry vs durable output.** Event/card setup and write failures fail open;
  descriptor publication failures remain extract-fatal.
- **Two contracts.** `process-run/v0` is run telemetry; `data-artifact/v0` is
  portable extract output. Composition is optional and one-way (terminal may
  reference published descriptors).
- **Platforms:** unchanged — linux amd64/arm64, darwin **arm64**, windows
  amd64/arm64. Intel-Mac users build from source.
- **Alpha:** interfaces may still change between minor releases; external pull
  requests are welcome.

## Migration guidance

No migration is required for existing recipes or runs. Defaults stay
byte-compatible until you opt in.

**Minimal enable** (card + stream under the platform runtime directory):

```bash
sumpter recipes run extract-multi \
  ./recipes/summary ./recipes/line-items \
  --file-list ./inputs.txt \
  --output-path ./out \
  --process-run
```

To adopt more deliberately:

1. Obtain a contract base that matches the pinned process-run/v0 material (same
   Crucible pin family as data-artifact) when your environment requires an
   explicit local bundle.
2. On `extract-multi`, pass `--process-run` (card + stream under the runtime
   dir), and/or `--process-run-events <path>` for an explicit stream-only path.
3. Optionally combine with `--artifact-descriptor --contract-base <dir>` so the
   terminal event can carry `data.artifacts[]` after successful publish.
4. Always treat the **terminal event** as authoritative for run outcome —
   `done == total` on progress alone is not success.

See [Process-run producer notes](../process-run.md) for flag and layout detail.
